## Choosing the right storage mechanism

The browser offers three main client-side storage APIs for persistent data. They serve different purposes and complement each other — the key is picking the right one for each use case.

| Storage | Best for | Data type | Async? | Approximate size |
|---|---|---|---|---|
| **Cache API** | HTTP responses, static assets | Request/Response | Yes | Large (GBs possible) |
| **IndexedDB** | Structured app data, offline records | JS objects, blobs | Yes | Large (GBs possible) |
| **localStorage** | Tiny config strings, UI preferences | String only | No (synchronous) | ~5 MB |

## Cache API

The Cache API stores `Request`/`Response` pairs. It is shaped like HTTP — the key is a URL (or `Request` object) and the value is a `Response`. This makes it ideal for:

- Pre-caching static assets (HTML, CSS, JS, images) for offline use
- Runtime caching of API responses inside a Service Worker
- Serving stale content while a fresh version is fetched in the background

The Cache API is most useful in combination with a Service Worker. See the [PWA course](https://avetavos.github.io/pwa-from-zero-to-hero/en/service-workers/) for Service Worker caching patterns.

## IndexedDB

IndexedDB stores arbitrary JavaScript values (objects, arrays, blobs, typed arrays) in object stores with optional indexes. It is the right choice for:

- Offline app data: user records, messages, documents
- Large blobs: audio, video, images that are part of the app's data model
- Data that needs to be queried, sorted, or filtered client-side
- Any structured data that does not fit the URL-keyed HTTP model

## localStorage

`localStorage` stores string key/value pairs synchronously. It blocks the main thread on every read and write. Despite its convenience, it is only suitable for:

- Tiny preferences: theme choice, language, a single token
- Values read on every page load where the synchronous access is acceptable
- Anything under a few kilobytes

Never store large objects or do frequent writes in `localStorage` — it will stall rendering.

<Callout title="Key point">
Use the Cache API for anything that looks like an HTTP response (URL + headers + body). Use IndexedDB for application records and blobs that need to be queried or updated. Use localStorage only for lightweight string preferences that must be read synchronously at startup. For PWA offline strategies, Cache API and IndexedDB often work together — assets in Cache API, app data in IndexedDB.
</Callout>

## Trade-offs

| Choice | Benefit | Cost |
|---|---|---|
| Cache API for HTTP responses | Matches the `Request`/`Response` model directly — good fit for pre-cached assets and API responses | Not a good fit for structured data — use IndexedDB instead when you need to query or index it |
| IndexedDB for app data | Query, index, and transaction support for complex data | Harder API to use — you manage schema versions and object stores yourself |
| localStorage for small preferences | Simple to read and write, synchronous syntax | Blocks the main thread on every access — unsuitable for large data or frequent writes |

## Common mistakes

- **Using the Cache API to store plain JS objects by JSON-stringifying them into a Response yourself** — unnecessary complexity; if the data isn't an HTTP request/response, reach for IndexedDB from the start.
- **Using localStorage for large data or an entire cache** — localStorage's synchronous I/O blocks the main thread and stalls the UI; move it to IndexedDB or the Cache API.
- **Assuming the Cache API and IndexedDB compete and you must pick one** — most PWAs use both together: Cache API for assets, IndexedDB for app data.

<Callout title="Real-world example">
**Twitter Lite (PWA)** — used the Cache API to store its app shell (HTML/CSS/JS) for fast loads, and IndexedDB to store timeline data and user records that needed to be queried. Source: [web.dev case study, "Twitter Lite PWA significantly increases engagement and reduces data usage"](https://web.dev/case-studies/twitter).
</Callout>
